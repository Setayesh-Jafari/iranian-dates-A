# راهنمای عملیاتی و استقرار

## وضعیت و پیش‌شرط‌های واقعی

کد برای استقرار مشروط آماده است، اما انتشار عمومی پیش از تهیه پایگاه‌داده، دامنه، ورودی امن، محتوای تأییدشده و فرایند رسیدگی به درخواست‌ها توصیه نمی‌شود. هیچ دامنه، حساب، گواهی، موجودی، قیمت یا اطلاعات تماس واقعی توسط این مخزن تأیید نشده است. هیچ داده، حساب یا سرویس واقعی در تست‌ها استفاده نشده است.

مدل تجاری فعلی **استعلام قیمت** است. فیلتر/مرتب‌سازی قیمت، نمایش INR و تبدیل ارز عمداً وجود ندارند: ستون‌های قدیمی `price` و `compare_at_price` ارز یا شرایط قیمت‌گذاری معتبری تعریف نمی‌کنند. قیمت صفر به قیمت واقعی تبدیل نشده و قیمت و موجودی از پاسخ عمومی محصول حذف شده‌اند. برای نمایش هر ارزی باید مالک ارز، واحد، اعتبار و منبع قیمت را تعریف و داده‌ها را تأیید کند. واحدهای مقدار استعلام: `kg`، `cartons` و `metric_tons` هستند.

## استقرار ایمن

1. PostgreSQL پایدار و پشتیبان‌گیری/بازیابی آزمایش‌شده فراهم کنید. `DATABASE_URL` را فقط از secret manager به سرور بدهید؛ TLS، شبکه خصوصی و حداقل مجوزهای DB را تنظیم کنید. Pool حداکثر ۱۰ اتصال در هر فرایند دارد؛ ظرفیت را برای مجموع instanceها محاسبه کنید.
2. قبل از استقرار، از DB نسخه پشتیبان بگیرید و در staging بازیابی را امتحان کنید. برای DB موجودی که جداول اصلی `products`، `reviews` و `inquiries` را دارد، با حساب migration مجاز فایل **`migrations/001_production_safety.sql`** را اعمال کنید. این migration تکرارپذیر است؛ جدول‌های محدودسازی، idempotency و ترجمه و پرچم انتشار را اضافه می‌کند و رکورد یا قیمت موجود را حذف نمی‌کند. برای DB خالی، ابتدا schema کامل را از `src/db/schema.ts` در محیط آزمایشی/با migration مدیریت‌شده بسازید؛ این فایل به‌تنهایی schema اولیه کامل نیست.
3. **انتشار محصولات:** در نسخه قبلی همه رکوردهای `products` عمومی بودند؛ برای جلوگیری از ناپدیدشدن ناخواسته کاتالوگ، migration هنگام افزودن ستون، رکوردهای موجود را `published=true` نگه می‌دارد. پیش از بازکردن سایت و indexing، مالک باید تمام رکوردهای موجود را بررسی و هر پیش‌نویس/داده خصوصی را `published=false` کند. رکوردهای جدید به‌صورت پیش‌فرض منتشر نمی‌شوند؛ پس از بررسی باید صریحاً `published=true` شوند. محصولات منتشرنشده در صفحات، API، sitemap، استعلام و ثبت نظر قابل دسترسی نیستند.
4. با یک ingress معتمد، HTTPS و دامنه اصلی را تنظیم و دسترسی مستقیم به پورت برنامه را مسدود کنید. ingress باید `Host` عمومی و `X-Forwarded-Proto` صحیح را ارسال کند و هدرهای مشابه دریافتی از کاربر را پاک کند. redirectهای دامنه فرعی/HTTP به دامنه اصلی باید در همین لایه با روش امن تنظیم شوند.
5. `RATE_LIMIT_IP_HEADER` را روی یکی از `x-real-ip`، `x-forwarded-for` یا `cf-connecting-ip` بگذارید. ingress **باید مقدار ارسالی کاربر را حذف و دقیقاً یک IP تأییدشده جایگزین کند**؛ فهرست IP و هدر نامعتبر رد می‌شوند. در غیر این صورت rate limit قابل دورزدن است. در Production بدون این تنظیم، IP معتبر یا DB، ارسال‌ها آگاهانه با 503 رد می‌شوند. برای حملات حجمی، محدودیت مستقل در WAF/ingress، سقف اندازه بدنه، timeout و پایش نیز لازم است.
6. `SITE_URL=https://دامنه-تأییدشده` را در runtime بگذارید. جایگزین `NEXT_PUBLIC_SITE_URL` است، ولی مقادیر `NEXT_PUBLIC_*` در build جاسازی می‌شوند و برای Docker باید هنگام build تنظیم شوند. پس از تأیید محتوا و دامنه، `SITE_INDEXING_ENABLED=true` را تنظیم کنید. بدون آن یا روی host متفاوت، صفحات `noindex` هستند و sitemap عمومی تبلیغ نمی‌شود؛ پیش‌نمایش نباید index شود. مقدار `SITE_URL` باید فقط origin بدون مسیر، query، credential یا fragment باشد.
7. محصول، ترجمه، عکس، مدارک، مشخصات، مسیر رسیدگی به استعلام، متن‌ها، شرایط حقوقی و اطلاعات تماس واقعی را قبل از انتشار تأیید کنید. seed صرفاً نمونه توسعه است و اطلاعات و تصاویر آن مدرک فعالیت واقعی نیستند. برای محتوای فارسی معتبر، جدول `product_translations` را با `product_id` و `locale='fa'` و متن‌های تأییدشده پر کنید؛ هر ترجمه باید دست‌کم نام و شرح غیرخالی داشته باشد. در نبود ترجمه، متن انگلیسی حفظ و زبان آن مشخص می‌شود؛ ترجمه خودکار ادعای تأییدشده نیست.
8. مسیرهای `/api/health`، فرم RFQ، بررسی نظر و sitemap را با داده تست غیرحساس در محیط staging/production بررسی و سپس پاک کنید. هشدار، log، دسترسی عملیاتی و پشتیبان را برای خرابی DB و شکست webhook فعال کنید.

**هرگز** seed مخرب را روی DB واقعی اجرا نکنید. `npm run db:seed` فقط با `ALLOW_DESTRUCTIVE_SEED=1` و خارج از `NODE_ENV=production` اجرا می‌شود و محصولات، نظرات و استعلام‌ها را پاک می‌کند. `drizzle-kit push` ممکن است schema/data را حذف یا تغییر دهد؛ آن را روی production اجرا نکنید. Startup کانتینر به‌طور پیش‌فرض schema یا داده را تغییر نمی‌دهد. در کانتینر production-mode، فعال‌کردن `RUN_SCHEMA_PUSH=1` بدون `ALLOW_UNSAFE_SCHEMA_PUSH=1` عمداً متوقف می‌شود؛ این override فقط برای DB دورریختنی است.

### بازگشت نسخه

ابتدا ترافیک را محدود و از DB پشتیبان تهیه کنید. جداول جدید را برای برگشت کد حذف نکنید. **نسخه قدیمی پرچم `published` را نمی‌شناسد و ممکن است پیش‌نویس‌ها را دوباره عمومی کند**؛ پیش از rollback، دسترسی کاتالوگ را محدود و این پیامد را رفع کنید. هر migration معکوس فقط پس از بررسی مالک داده و آزمایش بازیابی انجام شود.

## امنیت و عملیات

- ارسال RFQ و نظر JSON-only است؛ Origin ناسازگار، بدنه بزرگ، داده نامعتبر و honeypot رد می‌شوند. CORS عمومی فعال نیست. محدودیت ثابت مشترک PostgreSQL: ۱۰ استعلام در ۱۵ دقیقه و ۵ نظر در یک ساعت به ازای هر IP و scope. ثبت شمارنده اتمیک است و بین instanceها مشترک می‌ماند. این سامانه جایگزین WAF نیست.
- جدول `rate_limit_buckets` به‌جای IP خام، hash نگه می‌دارد؛ این hash همچنان داده بالقوه قابل‌شناسایی است. پاک‌سازی opportunistic انجام می‌شود؛ برای تضمین retention یک job محدودِ روزانه برای حذف bucketهای بیش از یک روز منقضی‌شده تنظیم کنید و نرخ/حجم آن را پایش کنید.
- کلید idempotency به‌همراه hash بدنه در `inquiry_submission_keys` ثبت می‌شود. کلید و RFQ در یک transaction ثبت و با حذف RFQ به‌صورت cascade حذف می‌شوند. برای ذخیره leads و hashها، retention، backup encryption و حقوق دسترسی متناسب با قانون قابل‌اعمال لازم است.
- RFQ فقط پس از commit موفق شناسه می‌دهد؛ در قطع DB پاسخ موفق ساختگی وجود ندارد. اتصال در لحظه commit ممکن است نامطمئن شود؛ کاربر می‌تواند همان داده‌ها را با همان کلید تکرار کند. فرم در همان صفحه و برای همان اطلاعات کلید را نگه می‌دارد؛ با reload کامل مرورگر تضمین تکرارنشدن حفظ نمی‌شود. یکپارچه‌سازی API باید برای هر تلاش منطقی `Idempotency-Key` تصادفی ۱۶ تا ۱۲۸ کاراکتری بفرستد و در retry همان کلید را حفظ کند؛ تغییر payload با همان کلید 409 می‌دهد.
- **نظرها ناشناس و تأییدنشده‌اند**: پروژه سامانه ورود یا تشخیص خریدار تأییدشده ندارد. ارسال عمومی فقط رکورد `pending` می‌سازد؛ هیچ مسیر عمومی برای تأیید/رد یا مشاهده نظرهای معلق وجود ندارد. تأیید یا رد فقط برای اپراتور دارای مجوز DB از طریق CLI `npm run review:moderate -- list|approve ID|reject ID` انجام می‌شود و امتیاز در transaction محاسبه می‌شود. خروجی `list` حاوی متن/نام است و باید در محیط خصوصی اجرا شود. اگر احراز هویت خریدار یا اثبات خرید الزامی است، قبل از فعال‌سازی عمومی نظرات باید سامانه هویت جداگانه طراحی شود.
- RFQ در جدول `inquiries` ثبت می‌شود. هیچ پنل مدیریت، ایمیل خودکار یا صف تضمین تحویل ساخته نشده است. `INQUIRY_WEBHOOK_URL` اختیاری، بهترین تلاش و بدون اطلاعات تماس خریدار است و پاسخ را حداکثر پنج ثانیه منتظر می‌گذارد؛ شکست آن ممکن است بی‌اطلاع تیم بماند. تیم باید دسترسی DB محدود، فرآیند بررسی منظم و در صورت نیاز سرویس اعلان قابل‌اعتماد/صف با مانیتورینگ فراهم کند.
- CSP شامل `unsafe-inline` است چون Next/انیمیشن‌های فعلی inline هستند؛ CSP سخت‌گیرانه مبتنی بر nonce نیاز به تغییر معماری دارد. HSTS در build production ارسال می‌شود و `includeSubDomains` عمداً فعال نیست. `ALLOW_EMBEDDED_PREVIEW=1` فقط برای build پیش‌نمایش iframe است و نباید در build عمومی استفاده شود؛ در حالت عادی `X-Frame-Options: DENY` و `frame-ancestors 'none'` فعال‌اند.
- دسترسی مستقیم به جداول inquiries، اطلاعات تماس، secretها و دستور moderation باید صرفاً به کارکنان مجاز محدود شود. فرآیند consent، اطلاعیه حریم خصوصی و سیاست نگهداری داده باید توسط مالک و مشاور حقوقی تهیه شود.

## تصاویر و SEO

فقط تصاویر محلی و `https://images.pexels.com` پذیرفته می‌شوند؛ URL خالی/نامعتبر و شکست بارگذاری به تصویر جایگزین محلی ختم می‌شود. تصاویر نمونه stock، تصاویر واقعی تأییدشده محصولات نیستند. قبل از استفاده از میزبان دیگر، هم `next.config.ts` (remotePatterns و CSP) و هم `src/lib/images.ts` را با allowlist دقیق به‌روز و مجوز تصویر را بررسی کنید.

sitemap در runtime محصولات منتشرشده را در هر دو زبان می‌خواند و canonical/hreflang دارد؛ در خرابی DB عمداً sitemap ناقص و موفق تحویل داده نمی‌شود. فرم inquiry و redirect قدیمی checkout ایندکس نمی‌شوند ولی robots.txt آن‌ها را برای خواندن noindex مسدود نمی‌کند. API از sitemap حذف و در robots مسدود است. مسیرهای 404 پاسخ 404/noindex می‌دهند؛ پوسته خطای Next ممکن است در HTML اولیه `<html lang/dir>` نداشته باشد و این دو پس از hydration برای فارسی تنظیم می‌شوند؛ این محدودیت برای کاربران بدون JavaScript و crawlerهای غیررندرکننده باقی است.

## تست محلی و CI

```sh
npm ci
npm run typecheck
npm run lint
npm test
npm run build
# فقط DB اختصاصی و دورریختنی که نامش به _test ختم می‌شود:
DATABASE_URL='postgresql://.../project_test' npm run db:push
TEST_DATABASE_URL='postgresql://.../project_test' ALLOW_TEST_DB_WRITES=1 \
  CHROME_PATH=/path/to/chrome BROWSER_REQUIRED=1 npm run test:integration
```

تست integration دو نمونه از standalone server و یک نمونه با DB قطع‌شده اجرا می‌کند و سپس داده‌های اختصاصی خودش را پاک می‌کند. workflow فعلی GitHub فقط typecheck، lint و build را اجرا می‌کند. نسخه پیشنهادی شامل PostgreSQL، audit، unit و مرورگر در `docs/extended-ci.example.yml` آماده است اما تا وقتی مالک دارای مجوز workflows آن را به `.github/workflows/ci.yml` منتقل نکند، خودکار اجرا نمی‌شود. اتصال GitHub این جلسه مجوز تغییر workflow نداشت. برای پایداری در sandbox بدون دسترسی به میزبان تصاویر، فقط پاسخ تصویرهای stock شبیه‌سازی می‌شود؛ درخواست‌های API، DB، مسیریابی و فرم واقعی‌اند. سرویس webhook خارجی، CDN، DNS و محیط production واقعی نیاز به آزمون جداگانه مالک دارند.
